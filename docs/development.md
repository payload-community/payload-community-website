# Website development

How the public website (`src/app/(frontend)`, `src/website`) is put together and what to keep in mind when changing it. Architecture details are in [`spec/architecture/frontend.md`](../spec/architecture/frontend.md).

## Translations (Lingui)

Every user-facing website string goes through a Lingui macro; the admin panel uses Payload's own `i18n` instead.

| Where | Use |
|---|---|
| JSX in server or client components | `<Trans>`, `<Plural>` from `@lingui/react/macro` |
| Attributes and strings inside components | `const { t } = useLingui()` from `@lingui/react/macro` |
| Async server components, `generateMetadata` | `const i18n = await initLingui()` (`src/lingui/server.ts`), then `i18n._(msg\`…\`)` |
| Module-level maps (labels, notices) | `msg` from `@lingui/core/macro`, resolved where they render |

Add a `comment` for short or ambiguous strings ("Apply", "Type"). Never call `i18n._({ id })` without a macro: the extractor cannot see it.

After changing strings, run `pnpm i18n:extract` and commit `src/locales/*/messages.po`. The compiled `messages.ts` is generated by `dev`, `build`, `typecheck` and `test:e2e` and is not committed. `pnpm lint` warns about unwrapped strings in website code (`lingui/no-unlocalized-strings`).

Vitest has no macro transform: keep pure helpers that unit tests import in macro-free files (for example `src/website/listing/params.ts`).

## Data access

- Public pages read with the Local API, `draft: false` and `overrideAccess: false` (no user), so access control decides what is visible.
- Listings parse their query string with `nuqs` loaders (`src/website/listing/params.ts`) and build `where` clauses in `where.ts`. Filters are plain GET forms and work without JavaScript.
- Detail pages load entries with `findEntryBySlug` (`src/website/detail.ts`); in draft mode they show the signed-in user's draft.

## Caching

- Listings are rendered per request.
- Detail pages are statically generated, revalidated every 5 minutes and on demand when the moderation hooks publish, change or delete an entry (`src/moderation/revalidate.ts`, [ADR-029](../spec/decisions/0029-website-page-caching-and-revalidation.md)). Use `safeRevalidate` (`src/website/revalidate.ts`) in hooks: they also run in the CLI and the jobs worker, outside Next.js.
- Section sitemaps are cached with tags `<section>-sitemap` for up to one hour.

## SEO

- Page metadata comes from `pageMetadata` (`src/website/metadata.ts`): title template, canonical URL, Open Graph and a default image (`/og-image.png`).
- `/robots.txt`, `/sitemap.xml` and the section sitemaps are route handlers that use `NEXT_PUBLIC_SERVER_URL` at request time ([ADR-030](../spec/decisions/0030-runtime-sitemaps-robots-and-default-og-image.md)).

## Tests

- E2E tests for the website are in `tests/e2e/website.e2e.spec.ts` and read the fixtures from `tests/helpers/websiteFixtures.ts`.
- The cookie banner hides itself from automated browsers; the consent test masks `navigator.webdriver`.
